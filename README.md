# Итоговый аналитический отчет (Лабораторная работа №1)

## 1. Резюме (Executive Summary)
В рамках лабораторной работы спроектирована базовая инженерная инфраструктура для разработки микросервиса «Расчет корзины и скидок». Проведен сравнительный анализ СУБД, настроен репозиторий GitHub с моделью ветвления и правилами защиты базовой ветки, внедрен автоматический контроль качества кода (CI Quality Gate) на базе GitHub Actions и `flake8`, выполнено обратное проектирование legacy-алгоритма с построением UML-диаграммы деятельности и подготовлен регламент Code Review.

## 2. Сравнительный анализ технологий

### 2.1. Матрица принятия решений

| Критерий | Вес | PostgreSQL (балл) | PostgreSQL (взвеш.) | MongoDB (балл) | MongoDB (взвеш.) |
| :--- | :---: | :---: | :---: | :---: | :---: |
| Поддержка ACID-транзакций | 0.35 | 5 | 1.75 | 3 | 1.05 |
| Целостность и типизация данных | 0.25 | 5 | 1.25 | 3 | 0.75 |
| Производительность агрегаций | 0.15 | 4 | 0.60 | 4 | 0.60 |
| Гибкость схемы данных (JSON/JSONB) | 0.15 | 4 | 0.60 | 5 | 0.75 |
| Стоимость владения и экосистема | 0.10 | 5 | 0.50 | 4 | 0.40 |
| **ИТОГО** | **1.00** | — | **4.70** | — | **3.55** |

### 2.2. Расчет и обоснование выбора
Формула взвешенной оценки: \(\text{Оценка} = \sum (\text{Вес}_i \times \text{Балл}_i)\).
* **PostgreSQL:** 0.35 × 5 + 0.25 × 5 + 0.15 × 4 + 0.15 × 4 + 0.10 × 5 = 4.70.
* **MongoDB:** 0.35 × 3 + 0.25 × 3 + 0.15 × 4 + 0.15 × 5 + 0.10 × 4 = 3.55.

**Обоснование:** победителем выбрана **PostgreSQL**. Хранение истории финансовых транзакций и баланса бонусных баллов требует строгих гарантий ACID и точной типизации (`NUMERIC`), чтобы исключить расхождения при конкурентных списаниях. При этом поддержка типа `JSONB` позволяет гибко хранить динамические параметры промокодов.

## 5. Обратное проектирование и планирование ревью

### 5.1. Анализ алгоритма
<img width="899" height="2136" alt="uml_diagram" src="https://github.com/user-attachments/assets/ae023357-77ff-440e-bf90-cd3897e83f2c" />


**Выявленные «запахи кода» (Code Smells) в legacy-фрагменте:**
1. **Магические числа (Magic Numbers):** порог суммы `15000`, множители `0.85`, `0.90`, `0.97`, `0.93`, `0.70` и скидка `500` зашиты в логику без именованных констант.
2. **Использование `float` для денежных расчетов:** умножение на числа с плавающей точкой (`0.85`, `0.97`) приводит к ошибкам округления копеек.
3. **Уязвимость к дублированию промокодов:** цикл `for p in promos` не проверяет уникальность элементов, позволяя применить скидку `"SUMMER"` несколько раз подряд, передав `["SUMMER", "SUMMER"]`.
4. **Отсутствие валидации входных данных:** нет проверки на отрицательную сумму корзины (`cart_sum < 0`) или некорректный уровень лояльности (`tier`).
5. **Отсутствие аннотаций типов (Type Hints) и документации (Docstring):** затрудняет понимание контракта функции без чтения ее реализации.

### 5.2. План code-review
Для предотвращения попадания дефектов в финансовую логику разработан регламент ревью модуля `src/discount.py`.
* **Ссылка на открытый Pull Request:** `[https://github.com/pull/3](https://github.com/Gusshin-Timofey/lab1-comprehensive-GushinTimofey/pull/4)`
* **Ключевые измеримые критерии:** отсутствие магических чисел, переход на `Decimal`, валидация входных аргументов, покрытие unit-тестами > 85%, прохождение `flake8`.
* **Механизм эскалации:** обсуждение в комментариях PR (до 24 часов) → короткий созвон при сохранении разногласий → финальное решение принимает Tech Lead.

## 6. Заключение
Внедренные инженерные практики минимизируют риски на всех этапах разработки: защита ветки `develop` и файл `CODEOWNERS` исключают бесконтрольное попадание кода в общую базу, автоматический Quality Gate отсеивает синтаксические и стилистические ошибки до начала ручного ревью, а формализованный план ревью с измеримыми критериями защищает бизнес-логику расчетов от финансовых ошибок и фрода.
